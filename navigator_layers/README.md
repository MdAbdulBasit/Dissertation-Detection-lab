# ATT&CK Navigator layers

Two layers, both generated by `scripts/build_navigator_layers.py` from `data/labelled_alerts.csv`.
**Neither file is hand-written.** Regenerate after any export:

```bash
python3 scripts/build_navigator_layers.py
```

Load at <https://mitre-attack.github.io/attack-navigator/> → *Open Existing Layer* → *Upload from local*.

| File | Setup measured |
|---|---|
| `01_default_ruleset.json` | Stock Wazuh 4.14.6, default Sysmon config |
| `02_custom_ruleset.json` | 37 custom rules; widened Sysmon config for T1112, T1070.004, T1003.001 |

## Scoring — derived from the data, not assigned

Each technique is scored on **detection quality** in its attack windows:

| Score | Meaning |
|---|---|
| **0** | **Blind** — no alert carries the technique ID *or its parent* |
| **1** | **Parent only / misattributed** — the behaviour is visible, the attribution is not |
| **2** | **Detected** — at least one alert carries the exact technique ID |
| **3** | **Detected and discriminating** — exact ID present **and** no benign alert carries it |

Tier 3 asks the question this dissertation exists to answer: does the detection also separate the
attacker from the administrator? It is deliberately hard to reach.

## The result

| | Default | Engineered |
|---|---|---|
| Blind | **7** | **0** |
| Parent only / misattributed | 1 | 0 |
| Detected at correct technique | 4 | **14** |
| Detected **and** discriminating | **3** | **1** |

Read naively that looks like a regression in the last row. It is not — it is the finding.

**The engineered ruleset eliminated every blind spot and did not improve discrimination at all.**
Thirty-seven rules converted seven invisible techniques and one misattributed one into fourteen
correctly-attributed detections, and the number that fire *only* on genuine attack activity went from
three to one.

And two of the default's three are qualified on the layer itself:

- **T1033** — `92022` correctly maps `qwinsta` to T1033, but `whoami`, the dominant variant, went to
  T1087 via `92032`. Partial coverage, not clean discrimination.
- **T1136.001** — `92040` (L12, T1136.001) requires `add\s`. The atomic writes `/add NAME PASS`; the
  mirror writes `NAME PASS /add`, where `add` is the final token with no trailing whitespace. The 10/0
  is **argument order, not intent**.

So on the honest reading it is **one genuine discriminator before and one after** — and both are T1105,
where the *vendor's* rules key on what was downloaded and where it landed rather than on how.

That is the measured warrant for a triage layer: rule engineering solves *coverage*. It does not solve
*discrimination*, because discrimination requires knowing intent, and intent is frequently absent from
the telemetry a rule can read. In T1003.001 it is absent entirely — the benign mirror runs a
character-identical command line and only the sensor's `targetImage` field distinguishes them.

## Caveats printed onto the layer

Every qualified score carries its caveat in the technique's `comment` field, so the figure cannot be
read without them. Four are qualified: T1136.001 and T1033 above, plus `T1112` (the exact-ID match comes
from `92041`, whose regex matches any `reg add … /d`) and `T1105` (the 40/0 is specific to this mirror —
an administrator downloading an installer with `curl` would trip `92074`).
